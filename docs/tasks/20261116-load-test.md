# k6 부하 테스트 기준선(baseline) 측정
- 브랜치: feature/load-test
- 상태: 대기
- **선행 조건: `feature/docker-compose` 머지** (앱·MySQL·Prometheus·Grafana 컨테이너 스택). 이 작업은 그 스택 위에서만 실행한다. → **충족**: PR #9로 main에 머지되었다.
- compose 확정값(`docker-compose.yml`, `docs/tasks/20261116-docker-compose.md`의 "다음 작업(feature/load-test)에 넘길 사실" 기준):
  - compose 파일: 저장소 루트 `docker-compose.yml`, compose project 이름 `mynotion`
  - 앱 서비스 `app`, 컨테이너 내부 포트 `8080` → k6 `BASE_URL=http://app:8080/api`
  - Docker 네트워크 `mynotion-net`(이름 고정) → `docker run --network mynotion-net`
  - Grafana `http://localhost:3000`(대시보드 uid `mynotion-overview`), Prometheus `http://localhost:9090`
  - 볼륨 초기화: `docker compose down -v`

## 배경 (왜 하는가)
1. **지금 성능을 말할 숫자가 하나도 없다.** `feature/observability`로 관리 포트 8081 `/actuator/prometheus`에서 `http_server_requests_seconds` 히스토그램, `hikaricp_*`, `jvm_*` 지표를 내보내게 됐지만, 부하를 준 상태의 값은 아직 측정한 적이 없다.
2. **2단계(Reminder N+1 해결, 페이징)의 before 수치가 필요하다.** `AGENTS.md` 로드맵은 단계마다 "문제 → 원인 → 해결 → 결과 수치"를 기록하라고 한다. 개선 전 수치가 없으면 개선 후 수치와 비교할 수 없다.
   - 이번에 재는 것: 일정 월별 조회·등록, 그리고 **대화 로그 페이징 before용 `GET /ai/chat-logs` 조회**(사용자 결정으로 범위에 추가).
   - 이번에 재지 않는 것: Reminder N+1. HTTP 요청이 아니라 `@Scheduled` 작업 안에서 생기므로 k6로 보이지 않는다. 2단계에서 운영 코드 계측과 함께 다룬다.
3. 그래서 이번 작업은 **성능 개선이 아니라, 개선 전 기준선을 처음 측정해 기록하는 것**이 목적이다. 코드는 그대로 두고 재현 가능한 측정 도구(k6 스크립트)와 결과 문서만 만든다.

> **학습 포인트**
> - **평균 대신 백분위(p95)를 본다.** 평균은 소수의 아주 느린 요청을 가린다. "100명 중 95명은 이 시간 안에 응답을 받았다"는 p95가 사용자 체감에 더 가깝다.
> - **기준선이 없으면 개선을 증명할 수 없다.** 같은 환경과 같은 시나리오로 before/after를 재야 "빨라졌다"가 숫자가 된다.
> - **부하 클라이언트(k6)와 서버가 같은 머신이면 한계가 있다.** k6도 CPU·메모리를 쓰므로 서버 성능만 순수하게 잴 수 없다. 그래서 결과는 절대값보다 **같은 조건에서의 상대 비교**용으로 쓰고, 측정 환경을 함께 기록한다.

### 2. 실행 방식: `grafana/k6` Docker 이미지 사용
- **결정: 호스트에 k6를 설치하지 않고 `grafana/k6` 이미지로 실행한다.**
  - 근거 ① 재현성: 누구든 Docker만 있으면 같은 k6 버전으로 실행할 수 있다. 버전은 `latest`가 아닌 **고정 태그**를 쓰고 README와 결과 문서에 적는다.
  - 근거 ② compose 스택과 같은 Docker 네트워크에 붙일 수 있어, 앱을 서비스 이름(`http://app:8080/api`)으로 호출할 수 있다. 호스트 포트 매핑에 기대지 않아도 된다.
  - 근거 ③ 선행 작업이 이미 Docker 기반이라 새 도구 설치가 늘지 않는다.
- 실행 예시 (README에 정리, 저장소 루트에서 실행. `<고정 버전>`은 구현 시 고른 태그로 채운다):
```bash
docker run --rm -i \
  --network mynotion-net \
  -v "$PWD/load-test:/scripts" \
  -e BASE_URL=http://app:8080/api \
  -e LOAD_TEST_PASSWORD="..." \
  grafana/k6:<고정 버전> run /scripts/baseline.js
```
- compose의 서비스로 k6를 추가하는 방식(profile 등)은 compose 파일 수정이 필요하므로 하지 않는다. 필요하면 질문/이슈에 남긴다.

### 4. 시나리오 (`baseline.js`)
**① `setup()` — 테스트 사용자·데이터 준비**
- `USER_COUNT`명을 `POST /auth/register`로 만든다. 이메일은 `${RUN_ID}-${i}@loadtest.local` 형식이다.
  - 요청 본문: `{"email": "...", "password": "<LOAD_TEST_PASSWORD>", "nickname": "loadtest-<i>"}`
  - 검증 규칙(`UserRegisterRequest`): `email` 형식, `password` 8자 이상, `nickname` 2~50자
  - 응답 `AuthResponse`: `{"accessToken": "...", "user": {...}}`. 회원가입 응답에도 토큰이 있다.
  - 이미 있는 이메일이면 `EMAIL_ALREADY_EXISTS` 에러가 난다. 이때는 `POST /auth/login`(`{"email", "password"}` → `accessToken`)으로 토큰을 받는다.
- 사용자마다 `POST /calendar/events`로 `READ_YEAR/READ_MONTH` 안에 일정을 `SEED_EVENTS_PER_USER`건 만든다(아래 ②의 요청 형식). 날짜는 그 달 안에서 고르게 나눈다.
- 사용자마다 `POST /ai/analyze`를 `SEED_ANALYZE_PER_USER`번 호출해 대화 로그를 쌓는다(`chat_logs` 시나리오용).
  - 요청 본문(`AiAnalyzeRequest`): `{"content": "loadtest 대화 로그 시딩"}`. `content`만 필수(`@NotBlank`)다.
  - 코드 확인 결과(`AiService.analyzeScheduleText`): 현재 **정규식 규칙 기반이라 외부 호출(OpenAI 등)이 없다**. 호출 1번에 `chat_logs` 2건(USER, ASSISTANT)과 `ai_actions` 1건이 저장되고, **일정(`schedules`)은 만들지 않는다**(초안만 응답하고 적용은 `/ai/apply`). 그래서 일정 조회 수치와 리마인더에 영향을 주지 않는다.
  - 응답 결과 유형(`PROPOSAL`/`NEEDS_CLARIFICATION`)은 내용 속 숫자에 따라 달라지지만 어느 쪽이든 대화 로그는 2건 쌓인다. `check`는 상태 200만 본다.
  - 대화 로그를 직접 넣는 API는 없다. 다른 생성 경로는 `/ai/revise`(내부에서 analyze 호출, 동일), `/ai/cancel`(1건, `draft`·`reason` 필요), `/ai/apply`(1건, **일정도 생성**하므로 쓰지 않음), `ReminderService`(SYSTEM 로그, 리마인더 대상 일정이 필요하므로 쓰지 않음)뿐이다.
- `setup()`은 `[{token}, ...]` 배열을 반환한다. **토큰과 비밀번호는 로그에 출력하지 않는다.**
- 별도 시딩 스크립트를 따로 두지 않고 `setup()`에서 처리한다. 데이터 양이 커져 `setup()`이 너무 오래 걸리면 질문/이슈에 남긴다.

**② VU 반복 — 읽기/쓰기 혼합 (scenarios 3개, 모두 `ramping-vus`)**
- VU는 `data[(__VU - 1) % data.length].token`으로 토큰 하나를 골라 `Authorization: Bearer <token>` 헤더로 보낸다.
- `read` 시나리오(일정 조회, VU의 60%): `GET /calendar/events?year=<READ_YEAR>&month=<READ_MONTH>`
  - `check`: 상태 200, 응답이 배열이고 길이가 `SEED_EVENTS_PER_USER` 이상
- `chat_logs` 시나리오(대화 로그 조회, VU의 20%): `GET /ai/chat-logs?limit=<CHAT_LOGS_LIMIT>`
  - 요청 형식(`AiController.chatLogs`): 쿼리 파라미터 `limit` 하나만 있다(`@RequestParam(defaultValue = "30") int limit`). 서버가 1~100으로 잘라 쓴다(`AiService.getChatLogs`). 요청 본문 없음, JWT 인증 필요.
  - 응답 형태: `ChatLogResponse` 배열 `[{"id", "role"(USER|ASSISTANT|SYSTEM), "content", "createdAt"}, ...]`, 최신순(`createdAt` 내림차순)
  - **외부 호출 없이 DB만 읽는다**(`@Transactional(readOnly = true)`, `ChatLogRepository.findByUserIdOrderByCreatedAtDesc` 한 번). `ChatLogResponse.from`은 지연 로딩되는 `user`를 건드리지 않아 N+1도 없다.
  - **페이징 before로 쓰는 이유**: 리포지토리가 사용자의 대화 로그를 **전부** 읽은 뒤 Java에서 `stream().limit()`로 자른다. 대화 로그가 많을수록 응답 크기는 같아도(30건) DB에서 읽는 행 수가 늘어난다. 2단계에서 DB 단 `LIMIT`/페이징으로 바꾼 뒤 같은 시나리오로 after를 잰다.
  - `check`: 상태 200, 응답이 배열이고 길이가 `min(CHAT_LOGS_LIMIT, SEED_ANALYZE_PER_USER × 2)`와 같음
  - 이 시나리오는 대화 로그를 새로 만들지 않으므로 측정 중 사용자별 대화 로그 수는 고정된다(일정 등록도 대화 로그를 만들지 않는다).
- `write` 시나리오(VU의 20%): `POST /calendar/events`
  - 요청 본문(`ScheduleRequest`): `{"title": "loadtest-...", "startAt": "2027-03-10T09:00:00", "endAt": "2027-03-10T10:00:00", "memo": "..."}`
  - `title` 필수, `startAt`·`endAt` 필수(`LocalDateTime`, 오프셋 없는 `yyyy-MM-ddTHH:mm:ss`), `startAt < endAt`이 아니면 `INVALID_TIME_RANGE`
  - `check`: 상태 200, 응답에 `id` 있음
  - 쓰기는 **조회 대상 월과 다른 달(`WRITE_MONTH`)**에 넣는다. 같은 달에 쓰면 테스트가 진행될수록 조회 결과가 커져 읽기 수치가 흔들린다.
- 각 요청에 `tags: { name: 'events_list' }` / `{ name: 'chat_logs_list' }` / `{ name: 'events_create' }`를 붙인다(결과 구분, threshold 대상 지정용). `setup()`의 시딩 요청에는 이 이름을 붙이지 않는다.
- 반복마다 `sleep(THINK_TIME_SEC)`를 둔다.

**③ 단계별 부하 (`ramping-vus`)**
- 워밍업(`WARMUP`, 0 → 목표) → 유지(`HOLD`, 목표 VU 유지) → 감소(`RAMPDOWN`, 목표 → 0)
- 목표 VU = `TARGET_VUS × (1 - WRITE_RATIO - CHAT_LOGS_RATIO)`(read), `TARGET_VUS × CHAT_LOGS_RATIO`(chat_logs), `TARGET_VUS × WRITE_RATIO`(write). 소수점은 반올림하고 최소 1로 한다. 기본값이면 read 12 / chat_logs 4 / write 4다.
- 두 비율의 합이 1 이상이면 read VU가 0 이하가 되므로 init 단계에서 실패시킨다.
- **결과 문서의 수치는 유지 구간 기준**으로 적는다. JIT 워밍업과 커넥션 풀 확장이 섞인 워밍업 구간은 제외한다.
- 참고: `ramping-vus`는 "동시 사용자 수"를 정하는 방식(closed model)이다. RPS는 입력값이 아니라 **결과값**이라서 서버가 느려지면 RPS도 같이 떨어진다. 결과를 해석할 때 이 점을 README에 짧게 적는다.

### 5. 테스트 데이터와 실행 환경 제약
- **compose 스택의 MySQL에서만 실행한다.** 운영 DB, 공유 DB에는 절대 실행하지 않는다. `BASE_URL`을 필수로 둔 이유다.
- 사전 데이터 월(`READ_MONTH`)과 쓰기 월(`WRITE_MONTH`)은 **현재 시각 기준 1시간 이내가 아닌** 고정 월로 정한다. `ReminderScheduler`가 매분 "1시간 안에 시작하는 일정"을 찾아 `ReminderLog`/`ChatLog`를 기록하므로, 지금과 가까운 일정을 만들면 리마인더 작업이 측정에 끼어든다.
- 기준선은 **빈 DB 상태(compose 볼륨 초기화 직후)**에서 1회 측정하는 것을 기본으로 하고, 측정 순서를 README에 적는다(볼륨 초기화 `docker compose down -v` → 스택 기동 `docker compose up -d --build` → 헬스 체크(`docker compose ps`에서 `app` healthy) → k6 실행).
- 로컬 `local` 프로필(H2)에서는 스크립트 디버깅용 짧은 스모크 실행(1 VU, 수십 초)만 허용한다. **H2 결과는 기록하지 않는다.**

### 6. thresholds (초기값 제안 — 기준선 측정 후 확정)
```js
thresholds: {
  'http_req_failed{scenario:read}': [`rate<${MAX_FAIL_RATE}`],   // 기본 0.01
  'http_req_failed{scenario:chat_logs}': [`rate<${MAX_FAIL_RATE}`],
  'http_req_failed{scenario:write}': [`rate<${MAX_FAIL_RATE}`],
  'http_req_duration{name:events_list}': [`p(95)<${P95_READ_MS}`],    // 기본 300
  'http_req_duration{name:chat_logs_list}': [`p(95)<${P95_CHAT_LOGS_MS}`], // 기본 300 (임시값)
  'http_req_duration{name:events_create}': [`p(95)<${P95_WRITE_MS}`], // 기본 500
  checks: ['rate>0.99'],   // 상수로 정의
}
```
- 시나리오·이름 태그로 범위를 좁혀서 **`setup()`의 회원가입(BCrypt로 원래 느림)과 시딩 요청(일정 등록, `/ai/analyze`)이 threshold에 섞이지 않게** 한다.
- `P95_CHAT_LOGS_MS` 기본 300ms는 일정 조회와 같은 읽기 요청이라 같은 값으로 둔 **임시값**이다. 사용자별 대화 로그 200건 전체를 읽으므로 일정 조회보다 느릴 수 있다.
- 위 숫자는 근거 있는 목표가 아니라 **임시 초기값**이다. 기준선 측정 후 사용자와 확정하고, 확정 전까지는 "임시값"이라고 README에 표시한다.

### 7. 결과 저장
- `handleSummary()`로 k6 summary를 `load-test/results/<RUN_ID>-summary.json`(전체)과 콘솔 텍스트 요약으로 저장한다. `results/`는 git에 올리지 않는다.
- 결과 문서에는 summary JSON에서 필요한 값만 옮겨 적는다.

## 질문/이슈 (Codex 작성)
아래는 PM(Claude)이 확인하지 못한 가정이다. 구현 전 또는 구현 중 확인하고 결과를 이어서 적는다.

- **[PM 사전 표시] compose 이름 미정** → **확인 완료**: compose 파일은 루트 `docker-compose.yml`(project 이름 `mynotion`), 앱 서비스 `app`, 네트워크 `mynotion-net`(이름 고정), 컨테이너 내부 포트 8080, Grafana `http://localhost:3000`(대시보드 uid `mynotion-overview`), Prometheus `http://localhost:9090`. 지시서의 꺾쇠 값을 모두 이 값으로 바꿨다(남은 `<고정 버전>`은 구현 시 고르는 k6 태그).
- **[PM 사전 표시] prod DB URL 고정** → **확인 완료**: `application-prod.yml`은 그대로 `localhost:3306`이지만, `docker-compose.yml`의 `app` 서비스가 `SPRING_DATASOURCE_URL=jdbc:mysql://mysql:3306/mynotion?...`으로 덮어쓴다. 이 작업에서 고칠 것은 없다.
- **[PM 사전 표시] 이번 시나리오가 "N+1 before"가 되지 않을 수 있음**: 코드 확인 결과 월별 조회(`findUserSchedulesInRange`)는 쿼리 1번이고 `idx_user_start` 인덱스를 쓰며, `ScheduleResponse.from`은 지연 로딩되는 `user`를 건드리지 않아 **N+1이 없다**. 2단계의 Reminder N+1은 HTTP 요청이 아니라 `@Scheduled` 작업 안에서 생기므로 k6 HTTP 지표로는 직접 보이지 않는다. 2단계 before 수치를 위해 (a) 리마인더 실행 시간·쿼리 수를 따로 재는 방법(커스텀 지표나 Hibernate statistics는 운영 코드 수정이라 범위 밖)과 (b) 대화 로그 페이징 before용 `GET /ai/chat-logs`(외부 호출 없이 DB만 읽음)를 이번 범위에 넣을지 사용자 결정이 필요하다.
  - → **사용자 결정**: (b) `GET /ai/chat-logs` 읽기 시나리오를 **범위에 추가**했다(4-②의 `chat_logs`). (a) Reminder N+1은 **이번 범위 밖으로 유지**하고, 2단계에서 운영 코드 계측과 함께 다룬다.
  - 참고: `/ai/chat-logs`도 N+1은 없다. 대신 사용자의 대화 로그 **전체를 읽고 메모리에서 `limit`으로 자르는** 문제가 있어 페이징 before로 쓰기에 맞다.
- **[PM 사전 표시] 로컬 머신 사양의 영향**: k6·앱·MySQL·Prometheus·Grafana가 한 대의 Mac(Docker Desktop)에서 같이 돈다. 결과는 머신·Docker 할당 자원에 크게 좌우되므로 절대값으로 쓰지 않고, before/after 비교는 **같은 머신, 같은 Docker 설정**에서만 한다. 측정 중 `docker stats`로 컨테이너별 CPU를 함께 기록할지 확인한다.
- **[PM 사전 표시] 쓰기 데이터 정리 방법**: 쓰기 시나리오와 `setup()`이 사용자·일정·대화 로그·AI 액션을 DB에 계속 남긴다. 기본안은 **측정 전마다 compose 볼륨 초기화**(`docker compose down -v`, project `mynotion`의 MySQL·Prometheus·Grafana 볼륨이 모두 지워짐)다. 볼륨 초기화가 다른 작업 데이터에 영향을 준다면, `RUN_ID`로 구분된 사용자만 남기고 `teardown()`에서 `DELETE /calendar/events/{id}`로 지우는 방식도 있지만, 삭제 요청이 지표에 섞이므로 권장하지 않는다.
- **[PM 사전 표시] Micrometer `uri` 라벨 값** → **확인 완료**: docker-compose 작업에서 `uri` 라벨에는 context-path `/api`가 붙지 않는 것을 확인했다(예: `/calendar/events`, `/auth/login`). 8절 PromQL 예시를 `/calendar/events`, `/ai/chat-logs`로 맞췄다.
- **[PM 사전 표시] 대화 로그 시딩이 `/ai/analyze`의 현재 구현에 기대고 있음**: 대화 로그를 직접 넣는 API가 없어 `setup()`에서 `/ai/analyze`를 호출해 쌓는다. 지금은 규칙 기반이라 외부 호출이 없지만, 3단계에서 LLM 연동이 들어가면 시딩이 외부 호출을 하게 된다. 2단계 after 측정은 3단계 전에 하는 것을 전제로 하고, 순서가 바뀌면 시딩 방법(예: 테스트 전용 SQL 시딩)을 다시 정해야 한다. 이번 범위에서는 운영 코드를 고치지 않는다.
- **[PM 사전 표시] 시딩 시간**: 기본값이면 `setup()` 요청이 회원가입 10 + 일정 300 + analyze 1,000건이다. `SETUP_TIMEOUT` 5분 안에 끝나는지 실제로 확인하고, 부족하면 이유와 함께 이 항목에 적는다.
- **[PM 사전 표시] thresholds·부하 기본값 근거 없음**: VU 20(read 12 / chat_logs 4 / write 4), p95 300ms(일정 조회)/300ms(대화 로그 조회)/500ms(일정 등록), 대화 로그 200건/사용자, 실패율 1%는 근거 없는 초기값이다. 기준선 측정 후 사용자와 확정한다.
- **[PM 사전 표시] k6 메트릭의 Grafana 표시**: 이번에는 서버 측(Micrometer) 지표만 Grafana로 본다. k6 자체 메트릭까지 Grafana에 올리려면 Prometheus remote write 수신 설정(compose 수정)이 필요하므로 범위 밖으로 둔다.
