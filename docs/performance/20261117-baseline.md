## 관찰 및 다음 단계에 쓸 점
1. **이 부하는 서버를 거의 쓰지 않는다.** 앱 CPU 평균 0.8%, Hikari 활성 커넥션 최대 1개, 대기 0이다. 20 VU + think time 1초의 closed model은 전체 약 20 RPS에 그친다. 따라서 이 기준선은 **저부하 응답 시간**이며, 처리 한계(포화점)는 측정하지 않았다.
2. **대화 로그 조회는 아직 일정 조회와 차이가 없다.** `/ai/chat-logs`는 사용자의 로그 전체를 읽고 메모리에서 `limit`만큼 자르지만, 사용자당 200건에서는 p95가 일정 조회와 비슷하다(11.49ms vs 10.85ms). 2단계 페이징의 before/after 차이를 보려면 사용자당 로그 수(`SEED_ANALYZE_PER_USER`)를 크게 늘린 조건을 **개선 전에 한 번 더** 측정해 두는 것이 좋다(이번에는 미측정).
3. **클라이언트와 서버 수치 차이**: 같은 구간에서 k6 p95가 서버 p95보다 약 1~2ms 크다. 네트워크·k6 처리 시간과 히스토그램 보간 오차가 섞인 값이다. before/after는 같은 쪽(클라이언트 또는 서버)끼리 비교한다.
4. 2단계 after 측정은 3단계(LLM 연동) 전에 해야 한다. 대화 로그 시딩이 `/ai/analyze`에 기대고 있기 때문이다.

## 측정 기록
- 1차 측정(00:51 시작)은 측정 도중 **Mac이 잠자기에 들어가**(전원 로그 01:10:40 Sleep, 이후 DarkWake) 처리량이 급감했고 k6 시나리오 시계가 멈췄다. 유지 구간이 오염되어 **수치를 버렸다**.
- 2차 측정(본 문서)은 `caffeinate -i -s`로 감싸 실행했고, 측정 구간(01:16:34~01:23:40) 전원 로그에 잠자기가 없음을 확인했다. k6 실제 소요 426초(시나리오 7분 + setup 약 4초)로 정상이다.
- 재현 순서: `docker compose down -v` → `docker compose up -d --build` → 4개 서비스 healthy 확인 → `load-test/README.md`의 `docker run` 명령에 `--out json=...`을 붙여 실행. 맥북은 덮개를 열어 두고 전원을 연결한다.
