## 정확성

### 🔴 1. 기본 RUN_ID가 setup과 결과 저장 시점에 각각 생성된다

- 위치: `load-test/lib/config.js:80`, `load-test/lib/config.js:134`, `load-test/baseline.js:59`, `load-test/baseline.js:170`
- 문제: `RUN_ID`를 생략하면 모듈 초기화 때마다 `Date.now()`로 새 식별자를 만든다. setup이 만든 이메일 접두어와 summary 파일 접두어가 일치하지 않는다. README 명령처럼 환경 변수로 명시하면 발생하지 않지만, 문서화된 선택 입력의 기본 동작은 잘못된다.
- 이유: k6 v0.57.0은 setup을 임시 VU에서 실행하고, `handleSummary()`에도 별도 VU를 만든다. 각 VU에서 모듈을 다시 초기화하므로, 테스트 종료 때의 식별자는 계정 생성 때의 식별자와 달라진다. 결과 파일명으로 시딩 계정과 실행을 연결할 수 없다. 이는 현재 코드와 [고정 버전 Runner 구현](https://github.com/grafana/k6/blob/v0.57.0/internal/js/runner.go#L325)의 `HandleSummary`, `runPart`, `newVU`를 대조한 정적 결론이다.
- 수정 제안: setup에서 확정한 식별자를 반환 데이터에 담고, summary에서는 전달받은 setup 데이터의 식별자를 사용한다. 승인된 `[{token}, ...]` 반환 형태를 유지해야 한다면 배열 항목에 비밀이 아닌 `runId`를 함께 넣는 방법이 있다. 내보낼 JSON에서는 다음 항목처럼 setup 데이터 전체를 제거하고 식별자만 별도 메타데이터로 남긴다. `RUN_ID` 필수화로 계약을 바꾸려면 먼저 지시서의 질문/이슈에 제안한다.
- 검증 조건: `RUN_ID` 없이 짧게 실행했을 때 계정 이메일과 summary 파일의 접두어가 같아야 한다. 명시한 경우에도 입력값이 두 곳에 동일하게 반영되어야 한다.

## 보안

### 🔴 2. summary 전체 직렬화로 테스트 계정 JWT가 파일에 저장된다

- 위치: `load-test/baseline.js:118`, `load-test/baseline.js:174`, `load-test/README.md:134`
- 문제: setup은 `[{token}, ...]`을 반환하고, `handleSummary()`는 받은 `data`를 그대로 `JSON.stringify()`한다. k6 v0.57.0은 이 객체의 `setup_data`에 setup 반환값을 포함하므로, 결과 JSON에 모든 테스트 계정의 JWT가 평문으로 남는다. README의 토큰을 summary에 추가하지 않는다는 설명과도 어긋난다.
- 이유: [고정 버전 summary 변환 구현](https://github.com/grafana/k6/blob/v0.57.0/internal/js/summary.go#L92)은 setup 데이터를 역직렬화한 뒤 `m["setup_data"]`에 넣는다. 따라서 직접 토큰을 출력하는 코드가 없어도 현재 저장 경로로 유출된다. `results/`의 Git 제외는 로컬 파일·결과 공유를 통한 노출까지 막지 못한다. 비밀번호가 함께 저장된다는 근거는 없으며, 이 지적은 JWT에 한정한다.
- 수정 제안: 출력용 객체를 따로 만들어 `setup_data`를 제외한 뒤 저장한다. 메트릭·threshold·그룹·집계 옵션은 보존하고, 재현에 필요한 메타데이터는 비밀이 아닌 필드만 명시적으로 선택한다. README도 실제 저장 내용을 설명하도록 맞춘다.
- 검증 조건: 결과 JSON에 `setup_data`와 토큰 값이 없어야 하며, 메트릭과 threshold 결과는 유지되어야 한다. 검증 과정에서도 실제 토큰 값을 콘솔이나 보고서에 출력하지 않는다.

## 측정 신뢰성·성능 확인 결과

다음 사항은 정적 검토에서 지시서와 일치했다. 실행 통과를 의미하지는 않는다.

- API 계약: 회원가입의 `email/password/nickname`, 로그인의 `email/password`, 일정의 `title/startAt/endAt/memo`, analyze의 `content`, 대화 로그 조회의 `limit`가 DTO·컨트롤러와 맞는다. 인증·일정 생성 성공 상태는 실제 컨트롤러처럼 200을 검사한다.
- 중복 이메일: `AuthService.register` → `EMAIL_ALREADY_EXISTS` → 공통 예외 응답의 HTTP 409 경로와 일치할 때만 로그인한다. 다른 회원가입 실패를 로그인으로 가리지 않는다.
- 시딩 격리: 준비 요청에는 `setup_*` 이름을 쓰고, 실패율은 측정 시나리오 태그, 지연은 측정 이름 태그로 제한한다. setup에는 `check()`가 없어 전역 `checks`도 시딩 성공으로 희석되지 않는다. 전체 HTTP 집계에는 시딩이 포함된다는 README 설명도 맞다.
- 데이터 고정: 기본 조회 월 `2030-01`과 쓰기 월 `2030-02`가 분리되어 있고, 같은 연·월이면 init에서 거부한다. 현재 검토 시점에서 먼 월이라 새 일정이 리마인더 대상에 들어가지 않는다. 월을 바꿀 때의 주의 사항도 문서에 있다. 월별 말일 계산과 시딩 날짜 분산, 오프셋 없는 09:00~10:00 일정은 서비스의 시간 범위 검사와 맞는다.
- 대화 로그: 현재 analyze는 로그 2건과 AI 액션 1건을 저장하며 일정을 만들지 않는다. 조회 check의 `min(limit, 시딩 호출 수 × 2)`는 빈 DB 기준과 맞는다. 일정 생성도 대화 로그를 만들지 않는다. 재실행 시 누적·볼륨 초기화 필요성을 README에 명시했다.
- VU와 단계: 각 시나리오는 `ramping-vus`로 0 → 목표 → 유지 → 0을 따른다. 비율 합이 1 이상이면 거부하고, 반올림·최소 1을 적용한다. 기본값은 read 12 / chat_logs 4 / write 4이며, 작은 목표나 비율 0에서 합이 달라지는 점도 문서화했다. 토큰 순환 선택과 반복별 think time도 지시서와 맞는다.
- 결과 경로: `results/<RUN_ID>-summary.json`은 README의 `--workdir /scripts`, `load-test:/scripts` 마운트, 사전 디렉터리 생성과 일치한다. `load-test/.gitignore`는 `results/`를 제외한다. 단, 생략한 RUN_ID의 일관성은 필수 수정 1번에 해당한다.
- 집계 해석: summary는 전체 단계 집계이며 유지 구간 전용 값이 아니라는 설명이 있다. 시계열 JSON 출력과 시나리오 시작 이후 워밍업을 제외한 구간 추출 방법을 별도로 안내한다. closed model의 RPS와 VU 비율 한계도 설명한다.
- 범위·스타일: 변경은 `load-test/**`뿐이고 운영 코드·compose·루트 설정은 그대로다. k6 이미지는 `grafana/k6:0.57.0`으로 고정되어 있다. JavaScript 2칸 들여쓰기, 함수 30줄 이하, 주요 숫자 상수화, 한국어 주석을 지킨다. 주소·비밀번호 값 리터럴이 없고 필수 환경 변수 검증이 있다. 콘솔 코드에서 토큰·비밀번호 직접 출력은 없지만, 파일 출력은 필수 수정 2번에 해당한다.

## 검증 누락·인계

### 🟢 1. 실제 실행 완료 조건은 측정 담당자가 확인해야 한다

- 위치: `load-test/README.md:124`, `load-test/README.md:139`, `load-test/README.md:146`
- 문제: 이번 diff에는 실측 결과 문서가 없고, Docker 이미지 실행·setup 제한 시간·threshold 종료 코드·유지 구간 분석의 실행 증거도 포함되어 있지 않다. 리뷰어는 요청대로 실행하지 않았으므로 실행 성공을 판정할 수 없다.
- 이유: 이 항목은 스크립트 결함 판정과 별개인 완료 조건 인계다. README도 실제 측정을 측정 담당자에게 맡긴다고 명시한다. 정적 검토만으로 5분 setup 시간이나 컨테이너 쓰기 권한, 요청 발생·성공 여부를 보증할 수 없다.
- 제안: 필수 수정 후 Orchestrator가 빈 compose DB에서 세 시나리오·대화 로그 길이 check·summary 저장과 Git 제외·비밀값 미포함을 확인한다. 기본 threshold 결과와 `P95_READ_MS=1`의 실패 및 종료 코드 99, 필수 환경 변수 누락 시 요청 전 실패를 기록한다. 유지 구간의 k6 원본과 같은 시각의 서버 지표를 대조해 지시서의 `docs/performance/YYYYMMDD-baseline.md`를 작성하고, 기존 백엔드 테스트는 JDK 17로 확인한다. 미측정 값은 채우지 않는다.

## 학습 포인트

1. **init은 실행 전체에서 한 번만 도는 전역 초기화가 아니다.** k6의 단계·VU는 별도 런타임을 쓰므로, 실행 전체에서 같은 값이어야 하는 식별자는 명시적으로 전달해야 한다. [공식 생명주기 문서](https://grafana.com/docs/k6/latest/using-k6/test-lifecycle/)
2. **라이브러리가 전달한 객체도 비밀정보가 있을 수 있다.** 보고서 저장 전에 필드를 검토하고, 메트릭에 필요하지 않은 인증 데이터는 제거해야 한다.
3. **태그 격리와 시간 구간 격리는 별개다.** 시딩을 제외해도 워밍업·감소가 남으므로, 유지 구간 비교에는 시각이 있는 원본과 같은 구간의 서버 지표가 필요하다. [공식 결과 출력 문서](https://grafana.com/docs/k6/latest/results-output/)
